# 一次生成任务是怎么跑完的（精讲 · 第 1 课挂账）

> 挂账日期：2026-11-04。回头看的时机：**第 6 课（Celery）**。

## 0. 核心：这是 3 条并行的线，不是一个流程

| 线 | 干什么 | 耗时 |
|---|---|---|
| **线1 · HTTP 请求线** | 收活、落库、**立刻返回** | 十几毫秒 |
| **线2 · 后台任务线** | 真正去"生成" | 3 秒 ~ 几分钟 |
| **线3 · SSE 长连接线** | 每秒把状态推给前端 | 常驻 |

> **最大的误解点：HTTP 请求早就结束了，后台任务还在跑。**

## 1. 时间轴

```
━━━ 线1 · HTTP ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  POST /api/shots
     ├─ schema 校验 → service 业务判断 → store 落库拿到 ids
     ├─ background.add_task(tasks.run_shots, ids)   ← 只是排队，不执行
     ├─ ★ HTTP 响应返回前端（状态全是 pending）
     └─ ★★★ 请求结束，连接关闭

━━━ 线2 · 后台（同一进程，请求已返回）━━━━━━━━━━━━━━━
  uvicorn 开始执行 run_shots(ids)
     ├─ 并发闸门 sem=3 → 同时跑 3 个
     ├─ 每个：status=running → await generate()（sleep 3~8 秒）
     ├─ 返回后：写候选图到磁盘 → 落库 candidates → 算成本 → 落库
     ├─ 25% 概率抛错 → status=failed；否则 succeeded + 默认选中第一张
     └─ 闸门空出位置，下一个镜头接着跑

━━━ 线3 · SSE（常驻长连接）━━━━━━━━━━━━━━━━━━━━━━━━━
  每 1 秒：重新查库 → 拼 JSON → yield → 前端 setState → 进度条动
```

## 2. 四个关键点

**① `background.add_task` 只是排队。** Starlette 先发响应，再执行你 add_task 的函数。
它和 Express 的 `res.json(); setTimeout(...)` 是同一个思路。

**② 后台任务不是另一个进程。** `await asyncio.sleep()` 期间让出 CPU，但仍在同一进程。
后果（Celery 要解决的）：服务器重启任务丢失 / 不能横向扩展 / 长任务占着进程。

**③ SSE 推的是数据库快照。** `store.list_shots()` 在循环体里，每秒重查。
所以后台改了库，1 秒后前端自动看到；前端也不用订阅具体任务。

**④ 谁写谁读。** 写=线2（状态/候选/成本），读=线1 一次 + 线3 每秒。
**必须落库，不能放内存**——否则进程重启、多进程就不一致了。

## 3. 三句话版本

1. 接口只负责"收活 + 落库 + 立刻返回"，把生成丢到后台。
2. 后台任务推进状态机（pending → running → succeeded/failed），把候选图和成本写回数据库，失败自动重试最多 3 次。
3. 前端靠一条 SSE 长连接，每秒收一次数据库快照，所以进度条自己动，不用轮询。

## 4. 自检三问

1. 删掉 `tasks.py`，接口还返回 200 吗？→ **会**（add_task 的异常发生在响应之后），但不会有进度。
2. 后台任务跑到一半服务器重启？→ 任务丢失，状态卡在 `running`。Celery 解决这个。
3. 为什么不用轮询？→ 延迟、请求量翻倍、每次一个完整往返；SSE 服务端主动推且能断线重连。
